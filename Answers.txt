Section 1 - SRP


Q1. Reasons to change in the old BankAccount class

1. Changes if the email provider changes (sendEmail uses SMTP directly).
2. Changes if the database changes (saveToDatabase is written for MySQL).
3. Changes if the statement format changes (printStatement decides the layout).
4. Changes if the banking rules change (minimum balance, deposit and withdraw checks).
5. Changes if the logging format changes (the transactionLog strings are built inside deposit and withdraw).

So the one class had five different people who could ask for a change in it.


Q2. Job description for BankAccount

BankAccount should only keep the account details and change the balance safely when money is
put in or taken out.


Q5. Wrap-up

I ended up with four classes. BankAccount holds the data and does deposit and withdraw,
AccountRepository saves it, NotificationService sends the message and StatementGenerator builds
the statement text. This is easier to test because I can check deposit and withdraw without a
database or an email server being involved, so the test does not need any setup and it will not
fail because of something unrelated. If the bank moves from MySQL to something else I only touch
AccountRepository, and withdraw cannot break because of it. Each class is small enough that I can
read it and know what it is supposed to do.


Section 2 - OCP


Q1. What I would have to touch to add a 4th account type in InterestCalculator

The old InterestCalculator has one method, calculate(String accountType, double balance),
and the whole rate table is an if/else chain inside it.

To add a Salary account there I would have to:
- open InterestCalculator.java, which is already working and already tested,
- add one more "else if (accountType.equals("Salary"))" branch before the else,
- add the "return balance * 0.05;" line inside that branch,
- retest Savings and Current again, because I edited the same method they run through.

That is one existing file and one existing method changed for every new account type, and the
else at the bottom quietly returns 0.0 if I spell the type wrong.


Q5. Wrap-up for the Salary Account requirement

Brand new files: SalaryAccount.java and SalaryInterestPolicy.java.
Existing files I opened: only Main.java, to create the new account and pick its policy.
Zero existing policy classes were changed - SavingsInterestPolicy and CurrentInterestPolicy were
not opened at all, and the InterestPolicy interface stayed the same.

The NotificationService change works the same way. Bank asks for a NotificationService in its
constructor, so adding SMSNotificationService was a new file plus one line in Main, and nothing
inside Bank had to move.
